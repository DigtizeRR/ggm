# Dashboard Rich Text Editor UI Audit

## 1. Problem Summary

The WordPress Classic editor embedded in the dashboard can present misaligned or overlapping Visual/Text controls and toolbar controls. The issue is not caused by Disease data, persistence, authorization, or the Disease AJAX endpoint.

The dashboard applies broad form-control and universal reset rules to every descendant of `.ggm-management-editor` and `#ggm-dash`. Native WordPress editor elements are descendants of those containers. That overrides the Classic editor's intended textarea dimensions and removes native visual/focus treatment from TinyMCE controls. On narrow dashboard content widths, `overflow-x: hidden` also clips the native toolbar's intentional horizontal overflow behavior.

## 2. Affected Dashboard Pages

| Dashboard surface | Rich-text implementation | Audit classification |
| --- | --- | --- |
| Administrator → Diseases → Add/Edit | Dynamically initialized Classic editor | Affected by the shared dashboard CSS conflict; Disease uniquely exposes it through dynamic initialization. |
| Administrator → Workshops → Workshop Content | Server-rendered `wp_editor()` | Subject to the same CSS conflict. It is initialized while its dashboard tab starts hidden, adding a lifecycle risk. |
| Administrator → Workshops → Form Text Content | Server-rendered `wp_editor()` | Same as Workshop Content. |
| Administrator → Courses → Content | Server-rendered `wp_editor()` | Subject to the same CSS conflict and hidden-at-page-load lifecycle risk. |
| Administrator → Courses → Lessons | Plain `<textarea>` fields generated by JavaScript | Not a WordPress rich-text editor; no TinyMCE/Quicktags instance to repair. |
| Other dashboard member/admin pages | No WordPress rich-text editor found | Not affected. |

The wp-admin health-form and settings editors also use `wp_editor()`, but they are outside `/dashboard/` and must not be changed by this fix.

## 3. Current Editor Architecture

The dashboard intentionally uses the WordPress Classic editor stack: TinyMCE for Visual mode and Quicktags for Text mode. It does not use a custom rich-text editor or a REST editor.

- `public/class-ggm-public.php` calls `wp_enqueue_editor()` only when `ggm_dashboard_user_is_administrator()` passes.
- Workshop and Course templates invoke `wp_editor()` during PHP rendering with `media_buttons`, TinyMCE, and Quicktags enabled.
- The Disease template deliberately contains a raw `textarea.wp-editor-area`; `assets/js/ggm-dashboard-diseases.js` creates the native editor with `wp.editor.initialize(editorId, { tinymce: true, quicktags: true })` after the Disease editor tab becomes active.
- TinyMCE writes its toolbar/container and iframe into the page DOM. The iframe body is isolated, but the wrapper, Visual/Text controls, toolbar, Quicktags controls, and textarea remain subject to dashboard CSS.

## 4. Editor Initialization Flow

### Disease

`public/class-ggm-public.php` → `wp_enqueue_editor()` and `ggm-dashboard-diseases.js` enqueue → `templates/dashboard/admin/disease-editor.php` emits the textarea → click Add/Edit calls `openEditor()` → `activate('disease-editor')` makes `#tab-admin-disease-editor` display as a block → `ensureEditor()` calls `wp.editor.initialize()` → TinyMCE/Quicktags create their native controls.

The Disease implementation checks `tinymce.get(editorId)` before initialization and calls `wp.editor.remove()` when returning to the list. It does not initialize the same Disease instance twice during a normal open/edit/save flow, and it does not move native editor DOM after initialization.

### Workshop and Course

`public/class-ggm-public.php` → `wp_enqueue_editor()` → `templates/dashboard/layout.php` includes every protected dashboard section → Course/Workshop templates call `wp_editor()` while their `.ggm-tab` is initially `display: none` → WordPress initializes the static editor instances during page load. Their JavaScript only reads/writes TinyMCE content with `tinymce.get(...).getContent()` / `setContent()`; it does not re-create the instances.

This means Course and Workshop have a separate lifecycle weakness: their native editor initialises in a hidden tab. That is not the primary Disease cause, but it should be normalized as part of a central editor integration fix because hidden initialization can cache zero/narrow dimensions in some browser/TinyMCE combinations.

## 5. CSS Cascade Analysis

### Confirmed conflicting rules

| File | Selector / property | Current effect | Why it conflicts |
| --- | --- | --- | --- |
| `assets/css/ggm-dashboard.css` | `#ggm-dash .ggm-management-editor textarea { width:100%; max-width:500px; border:1px solid #cbd5e0; border-radius:8px; padding:10px; font:inherit; }` (within the combined line-82 selector) | Styles `.wp-editor-area`, including the Quicktags/Text textarea that belongs to the native editor. | WordPress's editor wrapper/container is meant to own the editor dimensions and borders. A 500px ceiling, card-form border, padding, and radius on the internal textarea makes Visual and Text mode use different geometry. |
| `assets/css/ggm-dashboard.css` | `#ggm-dash .ggm-management-editor input` and `select` in the same combined selector | Styles every nested native input/select, including any editor-provided controls that use those elements. | The selector was intended for dashboard form fields but has no exclusion for `.wp-editor-wrap`; it is structurally unsafe for a native widget. |
| `assets/css/ggm-dashboard.css` | `#ggm-dash *, #ggm-dash *::before, #ggm-dash *::after { box-sizing:border-box; }` (line 42) | Forces `border-box` on all TinyMCE/Quicktags wrapper descendants. | This is a broad reset applied with higher dashboard specificity. It can alter width calculations used by legacy Classic-editor wrapper/control CSS. |
| `assets/css/ggm-dashboard.css` | `#ggm-dash, #ggm-dash *, ... { box-shadow:none !important; text-shadow:none !important; }` (lines 1611–1624) | Removes native TinyMCE button focus/active/shadow treatments with `!important`. | Native `editor.css` uses shadows for some pressed/focus states and documents size compensation for them. This does not create data loss, but it makes the editor controls look broken and prevents native visual behavior. |
| `assets/css/ggm-dashboard.css` | `#ggm-dash :is(... button ...):focus-visible { outline:3px solid ... !important; }` (line 1639) | Replaces focus treatment of native mode/toolbar buttons. | The selector includes TinyMCE and Quicktags buttons. It is an accessibility style with overly broad scope, not an editor-layout fix. |
| `assets/css/ggm-dashboard.css` | `#ggm-dash { overflow-x:hidden; }`, and mobile `#ggm-dash .ggm-tab { overflow-x:hidden; }` | Clips descendants that need horizontal overflow. | Native TinyMCE's toolbar group intentionally uses horizontal overflow when controls cannot fit. The dashboard clipping converts that into hidden or crowded controls on tablet/mobile. |

### Relevant native behavior being overridden

Local WordPress `wp-includes/css/editor.css` owns `.mce-toolbar-grp`, `.mce-toolbar`, `.mce-btn`, and their button padding, margin, focus, active state, and overflow behavior. The native editor expects its own `.wp-editor-wrap`, `.wp-editor-tools`, `.wp-editor-container`, `.wp-switch-editor`, and TinyMCE hierarchy to control dimensions and containment. There are no dashboard selectors explicitly targeting those classes; the damage comes from the broad descendant rules above.

## 6. JavaScript Analysis

Disease JavaScript is not continuously repositioning controls and does not mutate the WordPress-generated toolbar DOM. It initializes after switching the Disease editor tab from `display:none` to `display:block`, checks for an existing TinyMCE instance before creating one, syncs with `tinymce.triggerSave()` before save, and removes the instance on back/cancel.

The Disease editor is therefore not double-initialized in its normal route. The only implementation-specific concern is that it uses a manually initialized raw textarea rather than server-side `wp_editor()`, so it has no declarative wrapper/settings in the template. That is valid WordPress architecture when `wp_enqueue_editor()` is present, but it should share a small, centralized dashboard editor helper/settings policy with any later dynamic editor.

Workshop and Course do not dynamically initialize editors. Their scripts only set/read existing instances. Their `wp_editor()` instances are created while hidden because the dashboard renders all tab sections at once. This lifecycle issue may exacerbate layout faults but is not needed to explain the Disease screenshot: Disease is activated before `wp.editor.initialize()`.

## 8. Root Cause

The root cause is a **shared dashboard CSS cascade conflict**, not a Disease-only JavaScript or data problem:

1. The generic manager control rule styles internal `.wp-editor-area` and any nested controls as if they were ordinary dashboard fields. Its `max-width:500px`, border, padding, and radius conflict with the Classic editor's wrapper-owned layout.
2. The dashboard-wide universal `box-shadow:none !important` rule strips native TinyMCE button state rendering.
3. Dashboard/tab `overflow-x:hidden` prevents a native toolbar from using its intended horizontal overflow on constrained widths.
4. Course and Workshop add a secondary, pre-existing lifecycle risk by initializing their server-rendered editors while hidden. Disease does not share that timing defect because it activates first.

The issue is dashboard-wide in CSS scope. Disease is the first clearly reported surface because its recently added dynamic editor made the broken integration visible; it did not introduce a Disease-specific malformed toolbar or duplicate TinyMCE initialization.

## 9. Proposed Fix

Implement one centralized dashboard-editor integration rule set in `assets/css/ggm-dashboard.css`, scoped below `#ggm-dash .ggm-management-editor .wp-editor-wrap`.

The fix should:

1. Exclude `.wp-editor-area`, `.wp-editor-wrap`, `.wp-editor-container`, and editor-owned controls from the generic manager input/textarea/select rule; retain the existing dashboard styling for direct dashboard form controls only.
2. Give only the native wrapper a responsive `display:block; width:100%; max-width:100%; min-width:0; margin-top:6px` integration boundary. Let WordPress own its borders, toolbars, mode tabs, iframe dimensions, and button geometry.
3. Restore the native editor's own box-shadow/focus/active treatment inside `.wp-editor-wrap` by narrowly overriding the dashboard shadow-reset and generic focus rule there. Do not use a global undo and do not use arbitrary fixed toolbar dimensions.
4. Allow horizontal scrolling only at the native toolbar group on constrained screens; retain dashboard shell containment. The editor wrapper/container must remain `max-width:100%; min-width:0`, while `.mce-toolbar-grp` can preserve its native overflow behavior.
5. Add a small shared JavaScript helper or event only if visual testing confirms hidden-initialization defects in Course/Workshop. The helper should initialize/refresh a static editor after its tab becomes visible, once per ID; it must not poll or continuously reposition controls.

No Disease-only CSS hack, custom editor, data change, or replacement of TinyMCE/Quicktags is justified.

## 12. Responsive Fix Strategy

Desktop and laptop: the native editor wrapper fills the available manager content width; its mode tabs remain aligned within the wrapper, and WordPress owns toolbar button dimensions.

Tablet: preserve `min-width:0` on dashboard/editor containers so flex/grid parents cannot force overflow. Allow the toolbar group—not the entire dashboard—to use native horizontal overflow where needed.

Mobile: retain the existing 16px dashboard-card padding. Keep the editor wrapper at `width:100%; max-width:100%`; do not force a fixed toolbar or iframe width. Ensure the native toolbar scrolls or wraps according to WordPress behavior rather than being clipped by `.ggm-tab { overflow-x:hidden; }`.

## 13. Native WordPress Compatibility

The proposed approach retains `wp_enqueue_editor()`, `wp_editor()`, TinyMCE, Quicktags, Visual/Text switching, native toolbar controls, and existing sanitization/content handling. It removes dashboard interference around the native widget rather than restyling its internals into a custom editor.

All overrides will be scoped under `#ggm-dash .ggm-management-editor .wp-editor-wrap`, so wp-admin editor pages, Elementor, and other WordPress pages retain their native styling.

## 14. Regression Risks

| Risk | Mitigation |
| --- | --- |
| Direct dashboard controls lose their styling when generic selectors are narrowed | Target only direct standard controls, then verify Course/Workshop/Disease forms. |
| Toolbar becomes horizontally scrollable on mobile | Restrict overflow to the native toolbar group and test touch scrolling; do not make the dashboard shell scroll horizontally. |
| A shadow-reset exception visibly differs from dashboard cards | Limit it to native editor controls, which should intentionally look like WordPress controls. |
| Course/Workshop editor initialized while hidden remains dimensionally stale | Test after tab activation; add one idempotent visible-tab refresh only if required. |
| Rich editor content fails to sync | Do not change the existing `tinymce.triggerSave()` or read/write behavior. |
